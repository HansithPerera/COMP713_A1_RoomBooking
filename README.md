# Room Booking – Distributed Web/API Application

COMP713 Distributed and Mobile Systems – Assessment 2, Option A.

## Project overview

A small client–server system for booking study rooms by the hour.

- **Server:** a REST API built with FastAPI (Python) that stores rooms and
  bookings in a SQLite database.
- **Client:** a single web page (plain HTML + JavaScript `fetch`) served by the
  same server. Several browsers can use it at the same time; they all share one
  database.

The server is split into layers:

| File | Layer | Responsibility |
|------|-------|----------------|
| `main.py` | HTTP layer | Routes, status codes, error handlers, request logging |
| `service.py` | Application logic | Input validation and business rules; raises `ValidationError` (400), `NotFoundError` (404), `ConflictError` (409) |
| `repository.py` | Data access | Parameterised SQL (`?` placeholders only) |
| `db.py` | Persistence | Connection handling, schema, seed data |
| `static/index.html` | Client | Browser UI |

Business rules: rooms can be booked in whole hours between 08:00 and 22:00,
the booker's name is 1–50 characters, the date must not be in the past, and a
booking may not overlap another booking of the same room on the same date
(back-to-back bookings such as 10–12 and 12–14 are allowed).

All errors are returned as JSON in one shape: `{"error": "message"}`.

## Software required

- **Python 3.10 or newer** (developed and tested with Python 3.14.0)
- pip (comes with Python)
- A web browser
- Optional: VS Code with the **REST Client** extension (`humao.rest-client`)
  to run `requests/bookings.http`

No database server is needed – SQLite is built into Python.

## Setup

From the project folder:

**Windows (PowerShell)**

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

**macOS / Linux**

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Running

With the virtual environment activated:

```bash
uvicorn main:app --reload --port 8000
```

Then open **http://localhost:8000** in a browser.

- The web client is at `http://localhost:8000/`
- Interactive API docs (generated by FastAPI) are at `http://localhost:8000/docs`

Every request is logged in the server console, e.g.

```
[http] POST /api/bookings -> 201 (12.3 ms)
[http] POST /api/bookings -> 409 (4.1 ms)
```

## Configuration

| Environment variable | Default | Meaning |
|---|---|---|
| `BOOKING_DB_PATH` | `booking.db` (in the folder you start the server from) | Path of the SQLite database file |

The database file and its tables are created automatically on startup, and
three rooms are seeded if the database is empty. Delete `booking.db` to start
again with no bookings.

## API endpoints

| Method | Path | Success | Error responses |
|--------|------|---------|-----------------|
| GET | `/api/rooms` | 200 – list of rooms | 503 database unavailable |
| GET | `/api/rooms/{room_id}/bookings?date=YYYY-MM-DD` | 200 – bookings for that room and date, sorted by start hour | 400 missing/invalid date or non-numeric room id, 404 room not found, 503 |
| POST | `/api/bookings` | 201 – the created booking (with its `id`) | 400 invalid input, 404 room not found, 409 time overlaps an existing booking, 503 |
| DELETE | `/api/bookings/{booking_id}` | 204 – no content | 400 non-numeric id, 404 booking not found, 503 |

POST body example:

```json
{
  "room_id": 1,
  "booker_name": "Alice",
  "date": "2026-10-01",
  "start_hour": 10,
  "end_hour": 12
}
```

POST returns **400** when: `booker_name` is missing, blank or longer than 50
characters; `date` is not a valid `YYYY-MM-DD` date or is in the past; an hour
is missing or not a whole number; `start_hour` is before 8 or `end_hour` is
after 22; `end_hour` is not later than `start_hour`; or the body is not valid
JSON.

Unknown URLs return 404 and unexpected server errors return 500, both in the
same `{"error": ...}` shape.

## How to test

### 1. Automated tests (pytest)

With the virtual environment activated, from the project folder:

```bash
pytest -v
```

Each test uses its own temporary database, so your `booking.db` is never
touched. There are 38 tests covering every endpoint and status code above.

### 2. REST Client requests

1. Start the server (see *Running*).
2. Open `requests/bookings.http` in VS Code (REST Client extension installed).
3. Click **Send Request** above each request, from top to bottom. Each request
   is labelled with the status code it should return (success, invalid input,
   not found, conflict, delete).

### 3. Manual steps in the browser

1. Open http://localhost:8000. The room list loads and today's date is selected.
2. Choose tomorrow's date and click **Show bookings** – the table is empty.
3. Enter a name, start hour 10, end hour 12, click **Book** – a green message
   with `HTTP 201` appears and the table shows the booking.
4. Click **Cancel** on that row – a green `HTTP 204` message appears and the
   row disappears.

## How to demonstrate error handling

Error messages appear in red in the browser with the HTTP status code, and the
server console shows the matching `[http] ... -> 4xx` log line.

| Status | How to trigger it in the browser |
|--------|----------------------------------|
| **400** | Leave the name empty and click **Book**; or set end hour lower than start hour; or start hour 6; or pick yesterday's date and click **Book**. |
| **404** | The browser only offers existing rooms, so use the REST Client file (requests 9, 10 and 14) or visit `http://localhost:8000/api/rooms/999/bookings?date=2030-01-01`. Also: open the page in two windows, cancel a booking in one, then click **Cancel** on the same (now stale) row in the other → `Error 404: Booking N not found`. |
| **409** | Book 10–12, then try to book 11–13 for the same room and date. |
| **503** | See below. |
| Network failure | Stop the server (Ctrl+C) and click **Show bookings** – an orange "Cannot reach the server" message appears (different from the red HTTP error). |

### 503 – database unavailable

Stop the server and start it with the database path pointing to a folder that
does not exist:

**Windows (PowerShell)**

```powershell
$env:BOOKING_DB_PATH = "C:\no-such-folder\booking.db"
uvicorn main:app --port 8000
# afterwards, go back to normal:
Remove-Item Env:BOOKING_DB_PATH
```

**macOS / Linux**

```bash
BOOKING_DB_PATH=/no-such-folder/booking.db uvicorn main:app --port 8000
```

The server still starts (it logs `[error] could not initialise database`).
Open http://localhost:8000: the page shows
`Error 503: Database unavailable, please try again later`. The server console
shows the real cause (`OperationalError: unable to open database file`), which
is never sent to the client. The automated test
`test_database_unavailable_returns_503` checks the same behaviour.

### Two browser windows – double-booking prevention

1. Open http://localhost:8000 in two browser windows side by side.
2. In both, choose the same room and tomorrow's date, enter hours 14 to 16
   and different names.
3. Click **Book** in window 1 → green `HTTP 201`.
4. Click **Book** in window 2 → red `Error 409: This room is already booked
   for part of that time`.
5. Click **Show bookings** in window 2 – it now shows window 1's booking,
   because both clients share the same server and database.

The overlap check and the insert run inside one `BEGIN IMMEDIATE` transaction
(`repository.insert_booking_if_free`). This takes SQLite's write lock before
checking, so even if two requests arrive at exactly the same moment, the second
waits for the first to commit and then sees its booking. Clicking by hand
cannot make two requests truly simultaneous, so the automated test
`test_concurrent_requests_cannot_double_book` fires 20 booking attempts for the
same slot in parallel threads and checks that exactly one succeeds.

## Known limitations

- **SQLite, single file:** the database is one file on the server's disk.
  SQLite allows only one writer at a time, which is fine for this scale but
  would not suit many simultaneous users; a production system would use a
  database server such as PostgreSQL.
- **Single server instance:** the system runs as one server process on one
  machine. It is not replicated or load-balanced, so if the server stops,
  every client loses access.
- **No authentication:** anyone who can reach the server can create or cancel
  any booking. Booker names are not verified.
- **Whole hours only:** bookings start and end on the hour (e.g. 10:00–12:00);
  half-hour slots are not supported.
- **No time zones:** dates and "not in the past" are based on the server's
  local date. The client does not update automatically when another user
  changes a booking; click **Show bookings** to refresh.
- **Fixed rooms:** rooms are seeded at startup; there is no API to add or
  edit rooms.
